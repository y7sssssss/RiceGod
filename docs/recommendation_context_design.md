# 会话推荐列表与连续追问

## 问题和行为

原实现从上一轮 `task_results` 中收集菜谱，按序号解析“第二道菜”。新请求会用 `Overwrite({})` 清空并重建这些任务结果，因此中间插入“谢谢”或文化查询后，原始推荐文本仍在 `messages` 中，但程序无法直接按序号定位原推荐列表。展开第二道的详情后，任务结果也只剩这一道，无法再稳定选择原列表第三道。

新增 `AgentState.last_recommendations: list[RecommendationGroup]`。它仍属于会话 State，与当前轮任务结果分开管理，没有增加新的记忆数据库。

| 字段 | 用途与生命周期 |
| --- | --- |
| `messages` | 会话中的聊天消息 |
| `task_results` | 当前轮任务执行结果，每轮重建 |
| `last_recommendations` | 最近一次成功展示的推荐列表，直到有新的非空推荐列表替换 |

每组保存 `task_id`、`label`、原始任务问题和有序 `records`。记录保留真实菜名及检索字段，序号定位使用数据库原始菜名，随后重新执行带当前条件的检索。早餐、午餐、晚餐使用对应标签，支持早饭、午饭、晚饭别称；其他多组使用“第1组”等标签。

## 更新规则

- 新的推荐结果至少有一组非空，按任务计划顺序保存各组。每组内部保持排序后的记录顺序；不依赖任务完成顺序或结果字典顺序。
- 普通对话、文化查询、指定菜名详情、从旧列表选择某道菜，均保留原推荐列表。
- 新推荐全部为空或失败时，保留最近一次成功展示的列表；部分组可用时，保存本轮分组，空组无法被当作有效菜谱选择。
- 序号追问只查询一道菜并提供详情，不会被“上次推荐的第二道怎么做”中的“推荐”重新识别为新推荐。
- 回答提示要求按组展示，每组从 1 重新编号。合成回答遗漏或打乱菜名顺序时，使用依据记录生成的有序内容，避免快照与展示顺序不一致。

例如：推荐三道 → 谢谢 → 第二道做法 → 第三道材料，后两次定位始终使用最初的三道。展示新的土豆推荐列表后，序号改为指向新的列表。

## 选择与澄清

序号路由和规划直接使用当前会话的快照，不依赖模型猜测编号对应菜名。支持“第二道”“我选第二道菜”“晚餐第二道怎么做”“第二组的第一道菜”等表达。普通“第二个问题”“第二个步骤”不视为推荐序号。

| 情况 | 回复 |
| --- | --- |
| 没有推荐快照 | 提示先推荐或直接指定菜名 |
| 多组推荐却只说第二道 | 要求说明分组 |
| 指定不存在或重复的分组标签 | 澄清分组，可按第几组选择 |
| 序号为零、超过该组数量、选择空组 | 说明数量或无可选菜谱，不查询其他菜凑数 |
| 一次指定多个序号 | 请先选一组中的一道菜展开 |

详情检索继续执行当前用户的过敏、忌口和明确新条件；选择快照不允许绕过过滤。新限制与所选菜冲突时返回无匹配结果，保留原快照，不另选其他菜。

## 作用域与持久化

快照与其他图状态一起使用用户和会话组成的 `_thread_key` 隔离。它不属于长期用户偏好，也不通过 `/chat` 入参注入。Checkpoint 序列化允许 `RecommendationGroup`，严格 Msgpack 模式下保持类型与顺序。

默认 Checkpointer 已改为官方 PostgreSQL 实现，推荐分组、顺序和消息随 State 持久化，服务重启后使用相同 `_thread_key` 继续选择。`ChatService` 先异步读取 Checkpoint，有消息时不重复从原始消息表补入历史。显式 `CHECKPOINT_BACKEND=memory` 模式重启仍丢失快照。

启用前只存在于内存的旧快照不会自动迁移。没有 Checkpoint 时，原始消息恢复只补聊天文本，不能恢复结构化推荐列表，序号追问会澄清。具体配置与跨重启验收见 [State 持久化设计](state_persistence_design.md)。

## 验证

`tests/test_recommendation_context.py` 覆盖寒暄后的第二道、详情后的第三道、文化查询后选择、新列表替换、分组选择、范围与空列表澄清、当前限制、用户与会话隔离、模型漏菜/重排的展示兜底，以及依赖任务完成顺序与展示顺序的区别。模块整理后的完整回归以严格 Msgpack 模式运行，159 项通过，包含原有排序、条件隔离与记忆写入确认用例；新增应用资源生命周期和会话并发检查。

可选真实模型和数据库检查：

```powershell
python -m scripts.verify_recommendation_followups
```

结果见 [真实链路验收](recommendation_followups_verification.json)：模块整理后再次验证，13 轮对话、29/29 项检查通过。脚本通过 FastAPI TestClient 调用实际接口处理器，模型、Neo4j、Milvus、PostgreSQL 均未替换，只使用独立 UUID 虚构用户并清理其消息和记忆。第二道、第三道和文化查询后的第一道分别用时 4.82、3.76、4.36 秒；分组追问分别用时 3.40、3.46 秒，只代表本轮运行，不是通用性能指标。具体检查通过不代表任意指代或总体问答准确率。

重启后的真实 TCP 接口复测见 [HTTP 连续对话验收](recommendation_followups_http_verification.json)，4/4 项通过：推荐三道 → 谢谢 → 第二道详情 → 第三道详情，两个详情来源分别对应原列表第二项和第三项，回复与 PostgreSQL 消息历史一致。虚构测试用户行已清理。
