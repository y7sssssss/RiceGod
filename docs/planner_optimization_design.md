# Planner 范围与调用优化

原流程对菜谱和文化路由通常都调用模型规划。固定真实评测中，21 次进入模型规划路径有 8 次因多个菜谱任务的原文范围重叠而回退，包括“用鸡蛋推荐三道家常菜”这样的单一需求。无效规划结果被丢弃，但用户仍承担了模型调用耗时。

## 哪些请求直接规划

`application/agents/planning_policy.py` 根据当前问题和已确定的路由选择规则路径：

- 单一菜谱推荐或指定菜名详情；多食材是同一任务的组合条件，返回几道菜是数量，不是任务数。
- 明确分开的早餐、午餐、晚餐需求，最多四项，分别保留完整原文。
- 单个文化问题，直接交给文化检索任务。
- 单个菜谱需求并介绍“这道菜”的来历，构造菜谱任务与依赖它的文化任务。
- 普通对话和澄清沿用规则任务；序号选择继续通过会话推荐快照定位。

“分别”“对比”“替换”等复杂表达、多个菜谱动作或数量、多道已知菜名、独立的菜谱与文化需求，仍进入模型规划。规则选择是有限的结构识别，不是完整自然语言语义解析；新表达需要继续补评测。Router、回答和记忆模型调用不因这次优化一并关闭。

## 原文范围生成和修复

规划输入新增 `suggested_tasks`，提供程序识别的原文范围和依赖参考。提示词明确要求：一个查询需求对应一个任务，不能按推荐数量重复创建任务。

分餐范围由原问题中的实际位置生成；模型引用过短或整句重叠时，只有能唯一对应某一餐的原文或餐名，才恢复为该餐完整范围。任务顺序可以不同，不按列表顺序猜对应关系。

其他多任务在模型引用无效时，可用各自唯一、互不重叠的原文子问题恢复；若分别属于不同的分号、句号或换行分隔段，扩展到完整段，保留模型短引用遗漏的数量、口味和忌口。

重复或无法定位的原文、重复餐名映射、缺失分餐需求仍拒绝。原文覆盖校验、条件隔离、共享过敏限制、数量上限与依赖校验继续执行。模型计划深拷贝后再处理，校验成功后直接返回，避免重复做同一次条件构造。

## 观测和验证

规则路径记录 `planner mode=rules` 和 `reason`（如 `single_recipe`、`explicit_meals`、`dependent_lookup`）。范围修复记录 `planner_scope_repair task_count`，回退补充菜谱任务数；事件不保存用户原文或模型计划内容。

同一固定集版本 1.2 在修改前后比较；修改前的报告因产品规则变更对已有证据重新评分，原始执行耗时未改动，报告保留说明。新运行是真实执行，不是重新评分。题目、模型配置和本地菜谱 hash 一致不等于数据库、机器负载和提供商延迟完全一致，因此单次耗时差异只能描述本轮观测，不能直接作为普遍加速承诺。

补充集 [planner_cases.json](../data/evaluation/planner_cases.json) 检查非分餐独立需求、指定菜谱加独立文化查询，以及两道不同菜名详情，验证复杂请求仍能进入模型规划。

当前结果与对照见 [固定真实评测](fixed_evaluation_live.md)、[优化前基线](planner_baseline_live.md)和 [复杂规划验收](planner_evaluation_live.md)。

本轮全量回归 **257 项通过**（包含八项真实 PostgreSQL），实际 TCP HTTP 验收 **13/13** 项通过，本地 API 已重启加载修改。

原固定集真实 **36/36**、离线 **30/31**；固定题目的 Planner 模型路径次数由 21 次降至 0 次，普通图请求平均由 12.77 秒降至 6.26 秒。离线唯一失败仍是已有的同食材冲突未澄清，不归为本次范围修复成功。

三条复杂补充题目 **3/3** 通过、返回记录字段 **6/6**、推荐数量 **5/5**，三次均实际进入模型规划且没有回退。复杂请求平均仍为 **19.38 秒**，Planner 平均 **7.93 秒**；本次主要消除了明确请求的不必要规划，尚未证明复杂模型规划本身更快。两个评测集使用不同问题，不能直接把复杂集与原固定集的耗时比较为性能退化或改善。测试用户数据已清理。
